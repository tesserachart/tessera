# Usage and crash reports

Tessera sends the Tessera team anonymous crash reports from a fresh install, and usage analytics only after the user's first-run Yes, both through PostHog and both under one setting, `telemetry.consent` (`{"crashes": bool, "usage": bool | null}`, user-only, fresh `{"crashes": true, "usage": null}`). The runtime is the only part that sends: the window shapes its events and records its session with posthog-js and hands them to the runtime (`telemetry.capture`), and posthog-js sends nothing itself. Every event, recording batch and log record passes the log redactor, which also takes out account ids, logins and the account email. A build without a PostHog project (`TESSERA_POSTHOG_KEY`) asks nothing and sends nothing, and that is the sim's default.

## Sub-features

- `consent` is the terms screen's question "Share usage analytics", Yes or No with neither chosen, and under it the line "Tessera sends anonymous crash reports. Turn them off in Settings › App › Privacy." (while crash reports are on); Continue (or Accept with the terms) stays disabled, its tooltip "Choose Yes or No to share usage analytics first.", until the trader taps one. It is due in a build with a project while `telemetry.consent` usage is null, accounts on or off.
- `privacy-switch` is Settings › App › Privacy's two switches, shown in a build with a project: `Send crash reports` (consent crashes) and `Share usage analytics` (consent usage). Each off stops its part at once and leaves the other.
- `survey` is Settings › App › A question from the team: the project's running API survey (`telemetry.config`), with `Skip` and `Send`; once, ten minutes into a launch, a toast `One question from the Tessera team` with `Answer` leads there.
- `crash` is a runtime panic (posthog-rs panic capture, hook installed at start) or a window error (error boundaries, `onUncaughtError`, `error`, `unhandledrejection`, held until posthog-js loads), sent as `$exception` as the install with no person while crash reports are on, usage answered or not.
- `events` are app, area and panel opens, `chart loaded` and `account switched` from the window; the runtime's tool-call events (`TRACKED`: orders, positions, connections, analyst sessions, research, trade copier, journal, alerts, replay); `signed in` and `$identify` after a fresh sign-in, `signed out`.
- `traces` are each analyst turn's `$ai_trace`, `$ai_generation` and one `$ai_span` per tool call: names, times, tokens and outcomes, never words.
- `replay` is the window's session recording, on when the PostHog project records sessions. Every digit and input is masked, and all text in private areas, tiles and their menus.
- `logs` are the runtime's `info`+ logs from `tessera*` and `warn`+ from the rest, as OTLP JSON to PostHog Logs.
- `flags` are the project's feature flags (`telemetry.config`), read with `useFlag`; `analyst-trading-sessions` shows or hides Settings › Analyst › Trading sessions.

## How to get to it (user POV)

- First run in a build with a project: `dialog "One question before you go on"` (accounts off, as on the sim) or `dialog "Before you start"` (accounts on), its `radiogroup "Share usage analytics"` with `radio "Yes"` and `radio "No"`, neither checked, and `button "Continue"` or `button "Accept"`.
- Settings › App › Privacy: `switch "Send crash reports"`, `switch "Share usage analytics"`; the region `A question from the team` (when a survey is due). Report a problem there opens the feedback sheet (`feedback.md`); no report goes through PostHog.

## Driving it

- **The whole flow, in one go.** `scripts/usage-reports.ts [evidence dir] [ui dir] [--forward]` starts its own sim runtime with a project, behind a recording PostHog stand-in (`TESSERA_POSTHOG_HOST`): with `TESSERA_TEST_CRASH=1`: before answering it screenshots the first-run question (`first-run.png`), crashes a runtime task (`sim.crash`) and checks the `$exception` reached the stand-in with no usage event; it checks neither answer is chosen and Continue waits, taps Yes and Continue, comes back as a returning trader, adds the fake Rithmic login, switches to Paper 2 and buys, creates a copy group, opens the journal, research and markets, asks the stand-in analyst, answers the survey, checks Settings › Analyst with `analyst-trading-sessions` off, then turns `Send crash reports` off (`settings-privacy.png`) and crashes again: no new `$exception`. It writes `report.json` (every request by path and PostHog's status, each expected event's count, leaks of account ids, names, the question and the group name, digits left in recorded text), `sent.json` (every byte sent, the key taken out), a screenshot of each step, and beside each one (`<step>-replay.png`) the same moment played back from the recorded bytes with PostHog's own rrweb: what the trader saw and what PostHog got. `--forward` passes every request through to the EU project with `TESSERA_POSTHOG_KEY` (`gh variable get POSTHOG_PROJECT_KEY`) and records PostHog's real answers; the stand-in fills in only what the project does not have yet (replay on, the survey, the flag off) and marks those answers `stand-in`. Events land as `build: dev`, which the project filters out as test traffic. It prints VERIFIED only when every step ran, every expected event and a recording and a log batch were accepted, nothing private left and the page made no request of its own.
- **A build with a project in an e2e session.** The session's app command passes the runtime only `PATH`, `HOME`, the temp variables and those in `e2e.config.ts`'s `passEnv`, none of them `TESSERA_POSTHOG_KEY`, so a session never has a project; use the script above.
- **Crash reports only before the answer, nothing with both off.** Before answering, `settings.get '{"keys":["telemetry.consent"]}'` reads `{"crashes": true, "usage": null}`. To see nothing leave at all, turn `Send crash reports` off and answer No, then trace the runtime's sockets with `sudo strace -f -e trace=connect,sendto,sendmsg -s 200 -p <runtime pid>` (the pid from `ss -ltnpH '( sport = :<port> )'`), trade on Paper, switch areas, dispatch a window error and crash a task (below): the trace holds no `connect(` and no `posthog`, only the WebSocket's sends to the window. The page makes no request outside the runtime's origin.
- **A real panic.** Start the sim with `TESSERA_TEST_CRASH=1` and call `runtime.ts <port> sim.crash '{}'`: a runtime task panics and the runtime carries on (`{"crashed": true}`).
- **Yes.** Settings › App › Privacy's `Share usage analytics` on: the trace shows a DNS query for `eu.i.posthog.com` and a connection to it, and the project's activity shows the events within a few seconds; replays appear under Replay a minute or two after the session's first two seconds, logs under Logs.
- **Reading it back.** With a personal API key (`~/.config/tessera/posthog-admin.env`), HogQL through `POST /api/projects/<id>/query/` finds the run's events by `properties.$session_id`, and `GET /api/projects/<id>/session_recordings/<session id>/snapshots` its recording.

## Gotchas

- posthog-js keeps its opt-out flag in localStorage even with memory persistence; the window opts back in when it loads it again. With crash reports on and usage not yet Yes, posthog-js is loaded without the recorder; the Yes swaps in a recording instance when the project records sessions.
- Pop-out windows (a chart or the analyst popped out) do not report errors and are not recorded.
- PostHog takes no Windows PDBs: a Windows runtime's panic frames stay addresses.
- Replay starts only when the project's remote config has `sessionRecording` (PostHog › Settings › Replay); the window decides once, when sharing starts.
